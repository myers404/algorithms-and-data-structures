Primitives

Each primitive lists its main options side by side, then the questions where interviewers separate senior answers from staff answers.

Data placement

Partitioning

How does data get split across machines, and how does it move when the cluster changes?

OptionHow it worksBuys youCosts youReach for it when
Hash mod Nhash(key) % N nodesTrivial, even spreadChanging N reshuffles nearly every keyAlmost never at scale; fine when N is truly fixed
Fixed logical slotsHash into a fixed slot count (Redis Cluster uses 16,384), map slots to nodesRebalancing moves whole slots; small, simple routing mapSlot count chosen up front; slots can still be hotYou want predictable rebalancing and a tiny metadata footprint
Consistent hashing + vnodesNodes and keys on a ring; each node owns many virtual pointsAdding a node moves roughly 1/N of keys; no central map neededNo range scans; load variance without enough vnodesKey-value access only, peer-to-peer designs (Dynamo, Cassandra, caches)
Rendezvous (HRW) hashingEach key picks the node with the highest hash(key, node)Minimal disruption, no ring state, easy weightingO(N) per lookupSmall node counts: cache clients, shard pickers
Range partitioning, dynamic splitsSorted key ranges split on size or load; a placement service tracks themRange scans, ordered iteration, load-based splittingMonotonic keys hammer the last range; needs a metadata serviceScans matter (Bigtable, Spanner, CockroachDB, HBase)
Directory / lookup serviceExplicit key or tenant to shard mapping, cached by clientsArbitrary placement; move one big tenant on its ownDirectory is a dependency and a consistency problemMulti-tenant systems with very uneven tenants
Where depth is required
  • A single key gets 100x normal traffic. What do you do? (key splitting or salting, local caching, request coalescing, read replicas for that key)
  • Walk through adding a node while serving traffic. When does ownership flip, and what happens to in-flight writes?
  • Your keys are timestamps or auto-increment IDs. What breaks, and how do you fix it without losing range scans?
  • Secondary indexes: local per partition (scatter-gather reads) or global (separately partitioned, async updates)?
  • How does a client find the right partition, and what happens when its routing info is stale?

Shows up in: Distributed key-value store, Distributed cache, Distributed log / message queue, Distributed job scheduler, Metrics / monitoring system, Logging and tracing pipeline, Distributed rate limiter, Blob / object store, Service discovery / load balancing, Cluster resource scheduler, Stream processing engine

Replication

How many copies exist, who accepts writes, and what does a reader see?

OptionHow it worksBuys youCosts youReach for it when
Single leader, asyncLeader acks, then ships the log to followersLow write latency, simpleAcked writes lost on failover; stale follower readsLoss of a few seconds of data is tolerable
Single leader, sync / in-sync setAck only after some or all replicas persist (semi-sync, Kafka ISR)No loss of acked writesLatency tied to slowest required replica; availability shrinks with the setDurability matters and replicas share a region
Multi-leaderSeveral leaders (often one per region) replicate to each otherLocal writes everywhere, region independenceConflicts: LWW loses data, CRDTs constrain data types, custom merge is hardOffline or multi-region writes where conflicts are rare or mergeable
Leaderless quorumWrite to W, read from R of N; R + W > NHigh write availability, tunable per requestNot linearizable in practice; sloppy quorums weaken guarantees; needs read repair and anti-entropyAvailability over consistency, key-value workloads
Consensus group per shardRaft or Paxos log per partition; majority commitLinearizable, automatic safe failoverNeeds a majority; cross-region commits are slow; overhead per group (batch with multi-Raft)Correctness-critical data and metadata
Chain replicationWrites flow head to tail; reads from the tailStrong consistency with high read throughputA slow node stalls the chain; needs an external config masterRead-heavy strongly consistent storage
Where depth is required
  • The leader is partitioned but still thinks it is leader. How do you prevent split brain? (terms or epochs, leases, fencing)
  • A user writes then immediately reads from a follower. How do you guarantee read-your-writes? (session LSN tokens, leader reads, closed timestamps)
  • How do followers serve consistent reads without going through the leader? (leader leases, read index, follower reads at a safe timestamp)
  • Where do the replicas go? Walk through AZ and region placement and what a single AZ loss does to write availability.
  • A replica has been down for a day. How does it catch up? (snapshot plus log tail, log truncation limits)

Shows up in: Distributed key-value store, Distributed cache, Distributed log / message queue, Metrics / monitoring system, Distributed rate limiter, Blob / object store, Config / feature flag service, Service discovery / load balancing, Distributed lock service

Consistency and transactions

What guarantees hold when an operation spans multiple keys or partitions?

OptionHow it worksBuys youCosts youReach for it when
Single-partition transactions onlyDesign keys so atomic work lives in one partitionFast, simple, no coordinatorPushes cross-entity invariants into the applicationYou can pick partition keys around the invariants
Two-phase commitCoordinator runs prepare then commit across participantsAtomic across shardsBlocks if the coordinator dies after prepare; latency adds upCoordinator state is itself replicated via consensus (as in Spanner)
Percolator-styleTimestamp oracle plus locks and write intents stored with the dataSnapshot isolation over a sharded KV storeOracle is a bottleneck and a cross-region latency problem; lock cleanupBuilding transactions on Bigtable-like storage (TiDB)
Deterministic ordering (Calvin)Sequence transactions first, then execute in agreed orderNo 2PC aborts, high throughputNeeds read/write sets up front; awkward for interactive transactionsStored-procedure style workloads
SagasLocal transactions with compensating actionsNo distributed locking, works across servicesNo isolation; intermediate states are visibleLong-running, cross-service business processes
Isolation level choiceRead committed, snapshot isolation, serializable (SSI or 2PL)Weaker levels are faster with fewer abortsSnapshot isolation allows write skewPick per workload; name the anomaly you accept
Where depth is required
  • Give an example of write skew and how your design prevents it (or why it is acceptable).
  • Where do transaction timestamps come from, and what happens when clocks disagree?
  • Which data in this system needs linearizability, and which can be eventually consistent? Justify each.
  • What does the client see if the coordinator crashes mid-commit?

Shows up in: Distributed key-value store, Distributed log / message queue, Distributed job scheduler, Blob / object store, Cluster resource scheduler, Stream processing engine

Durability and redundancy

How do you survive disk, node, rack, and region loss at acceptable cost?

OptionHow it worksBuys youCosts youReach for it when
N-way replicationFull copies (usually 3) across failure domainsFast reads and repair, simple3x storageHot data, small objects, latency-sensitive reads
Erasure codingReed-Solomon k+m, e.g. 6+3 at 1.5x overheadSimilar durability at about half the costCPU for encoding; repair reads many nodes; worse tail latencyWarm and cold data at large scale
Locally repairable codesExtra local parity groups (Azure LRC)Common single failures repair from few nodesMore complex; slightly more overhead than plain RSVery large fleets where repair traffic dominates
Cross-region copiesAsync replication or erasure coding across regionsSurvives region lossEgress cost; replication lag windowCompliance or regional disaster requirements
Backups and snapshotsPoint-in-time copies isolated from the live systemProtects against corruption, bugs, and deletes, which replication copies faithfullyRestore time; stalenessAlways, alongside replication
Where depth is required
  • Do the durability math: disk failure rate, repair time window, probability of losing enough copies inside it.
  • How do you handle correlated failures? (placement across racks and power domains, staggered hardware batches)
  • How do you detect silent corruption? (end-to-end checksums, background scrubbing)
  • A bug deletes data and it replicates everywhere in seconds. What saves you?

Shows up in: Distributed key-value store, Distributed log / message queue, Metrics / monitoring system, Logging and tracing pipeline, Blob / object store, Stream processing engine

Coordination

Coordination and leadership

How do nodes agree on who owns what, safely, despite pauses and partitions?

OptionHow it worksBuys youCosts youReach for it when
Consensus storeetcd, ZooKeeper, or embedded Raft for leader election, membership, and configCorrect, well understoodLow write throughput; small data only; latency on every changeMetadata and control plane state, never bulk data plane traffic
LeasesTime-bounded ownership renewed by heartbeatOwnership recovers automatically when holders dieRelies on bounded clock drift; a paused holder may still actNearly any ownership: shards, jobs, leadership
Fencing tokensMonotonic token issued with each lease; storage rejects older tokensMakes leases safe against zombiesThe resource must check tokensWhenever a stale owner could corrupt state
Conditional writes / CASCompare-and-set on a version column instead of a lockNo separate lock serviceRequires store support; retries under contentionThe data store already supports it (most do)
Redis-based locksSET NX with TTL, or Redlock across instancesCheap and fastUnsafe for correctness under pauses and failoverEfficiency only, where duplicate work is harmless
Where depth is required
  • A worker holding a lease pauses for 30 seconds of GC, the lease expires, another takes over, then the first wakes up. What prevents double writes?
  • What state belongs in the consensus store, and what must stay out of it?
  • A watch disconnects and reconnects. How does the client avoid missing events? (resume from revision, relist if compacted)
  • Leadership flaps every few seconds. What causes it and how do you dampen it?

Shows up in: Distributed key-value store, Distributed log / message queue, Distributed job scheduler, Blob / object store, Config / feature flag service, Service discovery / load balancing, Cluster resource scheduler, Distributed lock service, Stream processing engine

Membership and failure detection

How does the system decide a node is dead, and what does that decision trigger?

OptionHow it worksBuys youCosts youReach for it when
Central heartbeatsNodes heartbeat to a coordinator that owns livenessSingle authoritative viewCoordinator load; one slow network path causes false positivesHundreds to low thousands of nodes
Gossip (SWIM)Random probes, indirect probes through peers, suspicion before deathScales to large clusters, no central pointEventual convergence; harder to reason aboutLarge peer-to-peer clusters (Consul, Cassandra)
Phi accrual detectorSuspicion level from heartbeat interval historyAdapts to network conditionsThreshold tuningVariable latency environments
Lease-based livenessA node is alive only while its lease is validTies liveness to ownership safetyConservative, slower detectionWhen a wrongly declared death is expensive
Where depth is required
  • A node is slow but not dead (gray failure). How do you detect and handle it?
  • Declaring a node dead triggers re-replication. How do you avoid a rebalancing storm from a 60 second blip? (separate routing failover from data movement, delay repair)
  • Asymmetric partition: A can reach B but B cannot reach A. What does your detector conclude?
  • How do new nodes join and get data without overloading existing ones?

Shows up in: Distributed key-value store, Distributed cache, Distributed log / message queue, Distributed job scheduler, Blob / object store, Service discovery / load balancing, Cluster resource scheduler, Distributed lock service, Stream processing engine

Time and ordering

How do you order events and resolve conflicts when clocks cannot be trusted?

OptionHow it worksBuys youCosts youReach for it when
Wall clock + NTPPhysical timestampsSimple, human meaningfulSkew silently breaks last-write-wins and orderingDisplay and metrics, never correctness
Per-partition sequenceOffsets or LSNs within a partition or logStrict order, cheapNo order across partitionsLogs, queues, replication streams
Lamport clocksCounter incremented and merged on messagesTotal order consistent with causalityCannot detect concurrent updatesTie-breaking ordering
Version vectorsPer-replica counters attached to valuesDetects concurrent writes preciselyGrows with number of writers; siblings pushed to clientsLeaderless stores that must not lose concurrent writes
Hybrid logical clocksPhysical time plus logical counterClose to wall time with causal orderingCorrectness assumes a max skew boundDistributed SQL without special hardware (CockroachDB)
Timestamp oracle / TrueTimeCentral monotonic service, or bounded-uncertainty clocks with commit waitStrict global order, external consistencyOracle is a hop and bottleneck; TrueTime needs special infrastructureGlobal transactions (TiDB TSO, Spanner)
Where depth is required
  • Two writes to the same key arrive at different replicas at the same time. Which wins, and is anything lost?
  • What ordering guarantee does your system actually give, and to whom? Per key, per partition, global?
  • Event time vs processing time: how do you handle data that arrives hours late? (watermarks, allowed lateness)
  • How do sequence numbers enable deduplication on retries?

Shows up in: Distributed key-value store, Distributed log / message queue, Distributed job scheduler, Metrics / monitoring system, Logging and tracing pipeline, Distributed rate limiter, Config / feature flag service, Distributed lock service, Stream processing engine

Storage and query

Storage engines

How are bytes laid out on disk given the read, write, and space profile?

OptionHow it worksBuys youCosts youReach for it when
LSM treeWAL + memtable, flushed to immutable SSTables, merged by compactionHigh write throughput, good compressionRead amplification (bloom filters help); compaction stalls; tombstonesWrite-heavy KV, time series, logs (RocksDB, Cassandra)
LSM compaction strategyLeveled vs size-tiered vs time-windowLeveled: less space and read amp. Tiered: less write ampLeveled: more write amp. Tiered: more space, more read ampLeveled for read-heavy, tiered for ingest, time-window for TTL'd time series
B-treeIn-place pages with WALPredictable reads, efficient range queriesRandom writes, page splits, fragmentationRead-heavy OLTP, relational databases
Append-only segments + indexSequential segment files with sparse offset index or in-memory hash indexSimple, sequential IO, page cache friendlyIn-memory index must fit RAM (Bitcask); needs compaction or retentionLogs, queues, simple KV
ColumnarColumn-oriented files with sparse indexes and heavy compressionFast scans and aggregations, 10x+ compressionPoint updates and deletes are expensiveAnalytics, logs, metrics rollups (Parquet, ClickHouse)
Object storage as primaryImmutable files on S3-like storage with local cachingCheap, elastic, very durableTens of ms latency, per-request cost, no in-place updateCold tiers, diskless brokers, lakehouse tables
Where depth is required
  • Explain read, write, and space amplification for your engine choice. Which one hurts this workload?
  • How do deletes work in an LSM, and what happens with a delete-heavy workload?
  • How does group commit trade durability for throughput, and what does fsync cost?
  • When does data move from local disk to object storage, and how do reads stay fast afterward?

Shows up in: Distributed key-value store, Distributed cache, Distributed log / message queue, Distributed job scheduler, Metrics / monitoring system, Logging and tracing pipeline, Blob / object store, Stream processing engine

Indexing and query execution

How do you find data fast without the index costing more than the data?

OptionHow it worksBuys youCosts youReach for it when
Full inverted indexTerm to posting list, per segment (Lucene)Arbitrary fast searchIndex can rival data size; costly ingest and mergesSearch where query flexibility is the product
Label index + brute-force scanIndex only labels or streams, scan compressed chunks (Loki)Very cheap ingest and storageSlow broad queriesLogs mostly queried by service and time range
Sparse primary index + skip indexesSorted data, index every Nth row, min/max or bloom per block (ClickHouse)Small index, fast filtered scansOnly fast when filters match the sort keyHigh-volume analytics and observability
Precomputed rollupsMaterialized aggregates at coarser resolutionLong-range queries become cheapLose detail; must choose dimensions ahead of timeDashboards over months of data
Scatter-gather with hedgingFan out to shards, merge results, send backup requests to slow shardsHorizontal query scalingTail latency grows with fan-outAny sharded query path
Where depth is required
  • Does the index fit in memory? Show the arithmetic.
  • A query fans out to 1,000 shards. What is your p99, and how do you control it? (hedged requests, partial results, limits)
  • How do you stop one expensive query from taking down the query tier? (cost estimation, per-tenant limits, query splitting)
  • How fresh is the index relative to ingest, and what does a user see in the gap?

Shows up in: Metrics / monitoring system, Logging and tracing pipeline, Blob / object store

Flow

Delivery semantics and idempotency

What happens to a message or job when something fails midway?

OptionHow it worksBuys youCosts youReach for it when
At-most-onceCommit progress before processingNever duplicatesLoses work on crashMetrics samples, telemetry where loss is fine
At-least-onceCommit progress after processing; retry on failureNever loses acked workDuplicates on retryThe default; pair with idempotent consumers
Idempotency keys + dedup storeRecord processed IDs with a TTL, check before applyingEffectively-once at the consumerDedup store cost; window must exceed max retry delayExternal side effects: payments, emails, API calls
Producer IDs + sequence numbersBroker drops repeated sequence numbers per producerDedup without a separate storeOnly covers producer to brokerLog and queue ingestion
Atomic output + offset commitWrite results and consumer offset in one transaction, or checkpoint state and offsets togetherExactly-once within the system boundaryNeeds transactional sink or checkpointing; ends at external side effectsStream processing (Kafka transactions, Flink checkpoints)
Transactional outboxWrite event to an outbox table in the same DB transaction; relay publishes itNo dual-write inconsistencyRelay lag; at-least-once publishingAny service that updates a DB and emits events
Where depth is required
  • Where exactly does your exactly-once guarantee stop?
  • A message fails every time. What happens to it and to the messages behind it? (retries with backoff, DLQ, head-of-line blocking)
  • Retries reorder messages. Does anything downstream depend on order?
  • How long must you remember idempotency keys, and what does that cost at your volume?

Shows up in: Distributed log / message queue, Distributed job scheduler, Logging and tracing pipeline, Config / feature flag service, Stream processing engine

Flow control and overload

What does the system do at 2x capacity, and does it recover afterward?

OptionHow it worksBuys youCosts youReach for it when
BackpressureBounded queues, credit or window-based flow controlProtects downstream, no unbounded memoryStalls propagate upstream to producersPipelines where slowing down beats dropping
Load sheddingReject early based on queue time, priority, or CPU; LIFO under overloadPreserves goodput for the work you acceptSome requests failOnline serving paths
Admission control + quotasPer-tenant rate and concurrency limits, weighted fair queuingIsolation between tenantsConfig burden; legitimate bursts get rejectedAny shared multi-tenant system
Retry disciplineExponential backoff with jitter, retry budgets, circuit breakersPrevents retry storms from amplifying failuresSlower recovery for individual requestsEvery client of every dependency
Deadline propagationPass remaining time budget down the call chainStops work nobody is waiting forEvery layer must honor itDeep call graphs
AutoscalingAdd capacity on load signalsHandles sustained growthLags spikes; cold starts; can scale into a dependency's limitsGradual load changes, never as the only overload defense
Where depth is required
  • Describe a metastable failure in this design: a trigger that goes away but the overload persists. How do you break the loop?
  • One tenant sends 50x their normal load. What do other tenants experience?
  • Retries at three layers each try 3 times. What is the amplification, and how do you prevent it?
  • The system recovers from an outage and every client reconnects at once. What happens?

Shows up in: Distributed key-value store, Distributed cache, Distributed log / message queue, Distributed job scheduler, Metrics / monitoring system, Logging and tracing pipeline, Distributed rate limiter, Blob / object store, Service discovery / load balancing, Cluster resource scheduler, Distributed lock service, Stream processing engine

Change propagation

How do changes reach the consumers that need them, and how do consumers catch up?

OptionHow it worksBuys youCosts youReach for it when
PollingConsumers periodically fetch current state or versionSimple, stateless servers, self-healingLatency vs load tradeoffLow change rates, many consumers, CDN-cacheable state
Watch / long-poll streamsServer pushes changes since a revisionLow latency, efficientConnection state; resume after compaction needs relistConfig, service discovery, orchestration (etcd, Kubernetes)
Pub/sub fan-outPublish to topic, broker delivers to subscribersDecouples producers from consumersSlow subscribers, delivery semantics, orderingMany independent consumers
Change data captureTail the database log (Debezium) into a streamNo dual writes; captures every changeSchema coupling to DB internals; ops overheadSyncing caches, search indexes, derived stores
Snapshot + deltaBootstrap from a full snapshot at a version, then apply deltasNew consumers join cheaplyMust coordinate snapshot version with stream positionAny consumer that can join late or fall far behind
Where depth is required
  • A consumer has been offline longer than the change log retention. How does it recover?
  • How does a cache know to invalidate, and what race lets a stale value win? (set after delete, versioned sets, leases)
  • A config change pushes to 100,000 clients in seconds. How do you limit blast radius if it's bad?

Shows up in: Distributed cache, Distributed rate limiter, Config / feature flag service, Service discovery / load balancing, Cluster resource scheduler, Distributed lock service

Control plane and data plane

How is the system managed, and does serving keep working when management breaks?

OptionHow it worksBuys youCosts youReach for it when
Imperative controlControl plane issues direct commands to nodesSimple and immediateLost commands leave drift; hard to recover partial failuresSmall systems, rare operations
Declarative reconciliationStore desired state; controllers converge actual state in level-triggered loopsSelf-healing, idempotent, resumableEventual; controllers can fight each otherOrchestrators, schedulers, placement (Kubernetes, Borg)
Push configControl plane pushes to data planeFast convergenceControl plane must track every nodeModerate fleets needing fast changes
Pull configData plane fetches from a cache or edgeScales well, data plane controls its own paceSlower convergenceVery large fleets
Static stabilityData plane caches last known good state and keeps serving without the control planeControl plane outage does not become a serving outageStale decisions until recovery; must bound stalenessNearly always, for anything in the serving path
Where depth is required
  • The control plane is down for an hour. What still works, and what degrades?
  • A controller bug decides to drain 80% of the fleet. What stops it? (rate limits on disruptive actions, minimum healthy thresholds)
  • How do you roll out a new version of this system with mixed versions running? (protocol and format compatibility)

Distributed key-value store

Distributed job scheduler

Staff-level themes

These cut across every prompt. Raising them unprompted, with specifics, is most of what separates staff from senior.

Static stability
The data plane keeps serving on last known state when control plane, metadata, or config systems fail. Say explicitly what survives each dependency outage.
Blast radius
Cells, shuffle sharding, staged rollouts, and per-tenant isolation. A bad deploy, bad config, or bad tenant should affect a bounded fraction of customers.
Multi-tenancy
Quotas at every shared layer (queue, storage, compute, query), fair scheduling, and per-tenant observability. Most real infra is shared.
Dependency loops
Monitoring must not depend on what it monitors. Rollback must not require the deploy system to be healthy. Check bootstrap order from a cold start.
Operational lifecycle
Rolling upgrades with mixed versions, on-disk format migrations, adding capacity live, draining nodes. "How do you upgrade this?" exposes whether a design is real.
Degradation modes
For each major component, what the user sees when it is slow, down, or wrong. Prefer partial results and stale data over hard failure where correctness allows.
Capacity math that decides things
Use the numbers to choose: whether the index fits in RAM, whether cross-AZ replication cost is acceptable, how many partitions are needed for target throughput.
Evolution
What a small team ships first, what breaks at 10x, and what the 100x design looks like. Name the signals that trigger each step.
Cost as a design axis
Storage tiering, erasure coding, cross-AZ transfer, and object storage economics. Staff candidates quantify cost alongside latency and availability.
