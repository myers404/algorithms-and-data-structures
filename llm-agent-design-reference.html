LLM agent design reference

Agent design questions are built from a small set of primitives: how control flows, how the model reaches tools and knowledge, how context and memory are managed, and how the system is kept reliable, safe, and affordable. Each primitive lists its options with tradeoffs, the questions that reveal depth, and where practitioners still disagree.

The tradeoffs here are durable. Product names, protocol versions, and numbers change quickly, so they are kept to a dated section near the end.

Shape of the system

Control flow and autonomy

How much of the path does code decide, and how much does the model decide at runtime?

OptionHow it worksBuys youCosts youReach for it when
Single call + contextOne model call with the right information suppliedCheapest, fastest, easiest to testNo recovery if information is missingThe task is answerable in one shot
Prompt chainFixed sequence of calls with code checks between stepsPredictable and debuggable; each step is simplerRigid; early errors carry forwardSteps are known in advance (extract, check, draft)
RouterA classification call picks a specialized path or modelFocused prompts; cheap models for easy casesMisroutes fail silentlyInputs fall into distinct categories
ParallelizationSplit into independent calls, or run the same call several times and voteLower latency, or confidence through agreementCost multiplies; merging is its own problemIndependent subparts, or high-stakes classification
Evaluator-optimizerGenerator and critic loop until criteria passQuality where criteria are clearLatency and cost; the critic can be wrongTranslation, code against tests, style compliance
Tool-calling loopThe model picks tools and decides when to stopHandles open-ended paths and recovers from errorsUnpredictable cost and latency; harder to testThe path cannot be known upfront
Plan then executeModel writes a plan, an executor follows it, replanning on failureReviewable plan; less drift; plan can be approvedPlans go stale when reality differsLong tasks, or plans that need sign-off
Graph with agent leavesExplicit nodes and edges in code, with loops inside some nodesVisible topology, checkpoints, deterministic where it mattersTopology changes are code changesProduction systems that need control and flexibility
Reference skeleton
def run_agent(llm, tools, task, max_steps=25, token_budget=200_000):
    messages = [{"role": "user", "content": task}]
    used, recent_calls = 0, []
    for _ in range(max_steps):
        reply = llm.generate(messages, tools=tools.schemas())
        used += reply.tokens
        messages.append({"role": "assistant", "content": reply.content})
        if not reply.tool_calls:
            return {"status": "done", "answer": reply.text, "tokens": used}

        results = []
        for call in reply.tool_calls:
            signature = (call.name, repr(sorted(call.args.items())))
            recent_calls = (recent_calls + [signature])[-6:]
            if recent_calls.count(signature) >= 3:        # stuck in a loop
                output = "You have made this exact call 3 times. Try a different approach."
            else:
                try:
                    output = tools.execute(call.name, call.args, idempotency_key=call.id)
                except ToolError as err:
                    output = f"Error: {err}"                # actionable, so the model can recover
            results.append({"tool_call_id": call.id, "content": truncate(output, 8_000)})
        messages.append({"role": "tool", "content": results})

        if used > token_budget:
            return {"status": "escalate", "reason": "token budget", "messages": messages}
    return {"status": "escalate", "reason": "step limit", "messages": messages}

def truncate(text, limit):
    text = str(text)
    if len(text) <= limit:
        return text
    return text[:limit] + f"\n[truncated {len(text) - limit} chars; narrow the query]"
Where depth is required
  • Why is an agent justified here rather than a workflow, and what evidence would change your mind? (unknown path length and error recovery; eval results comparing both designs)
  • How does the loop stop? (model signals completion, step and token budgets, no-progress detection, completion check)
  • The agent repeats the same tool call with the same arguments. How do you detect and break it? (call signature tracking, a corrective message, budget, escalation)
  • Which decisions would you move from the model into code? (anything with a deterministic rule: authorization, pricing, compliance)
Still debated
  • How much scaffolding to build. Elaborate graphs can age badly as models improve, while minimal harnesses lean heavily on model judgment.
  • Explicit planning steps vs letting the model plan inside its own reasoning.

Shows up in: Coding agent, Customer support agent, Browser or computer-use agent, Workflow automation agent, Voice agent

Multi-agent coordination

When does splitting work across agents pay for its extra cost and complexity?

OptionHow it worksBuys youCosts youReach for it when
Single agent, many toolsOne loop and one contextSimplest; all context in one placeContext fills up; tool selection degrades with large toolsetsThe default starting point
Orchestrator + sub-agentsLead plans and spawns workers with fresh contexts; workers return condensed findingsParallel exploration and context isolationMany times the tokens; briefs must be precise; duplicated effortBreadth-first research, broad searches
Sub-agent as a toolA worker invoked like a function that returns a resultClean interface, reusable, easy to traceShares nothing beyond the briefWell-scoped delegations (search a codebase, review a diff)
HandoffsControl transfers to a specialist that owns the conversationFocused prompts and tools per domainContext lost or duplicated at handoff; routing loopsSupport triage across distinct domains
Shared state (blackboard)Agents read and write a common storeLoose coupling, asynchronous progressConflicting writes, unclear ownershipPipelines with independent stages
Cross-boundary agents (A2A)Agents publish capability cards and exchange tasks with lifecyclesInteroperability across teams, vendors, and trust boundariesAuth, trust, and latency across boundariesThe peer agent is owned by someone else
Reference skeleton
async def research(llm, question, run_worker, max_workers=5, worker_timeout=300):
    plan = await llm.plan(question)             # [{"scope": ..., "avoid": ..., "output": ...}]

    async def worker(sub):
        brief = (f"Question: {question}\nYour scope: {sub['scope']}\n"
                 f"Out of scope (other workers cover it): {sub['avoid']}\n"
                 f"Return: {sub['output']}, with sources, under 1,500 tokens.")
        # Fresh context per worker: only the brief, its own tools and budget
        return await asyncio.wait_for(run_worker(brief), timeout=worker_timeout)

    results = await asyncio.gather(*(worker(s) for s in plan[:max_workers]),
                                   return_exceptions=True)
    findings = [r for r in results if not isinstance(r, BaseException)]
    failed = [s["scope"] for s, r in zip(plan, results) if isinstance(r, BaseException)]
    return await llm.synthesize(question, findings, gaps=failed)   # report gaps, don't hide them
Where depth is required
  • What exactly does the lead send a worker, and what comes back? (goal, scope, what to avoid, output format, budget; a short sourced summary rather than a transcript)
  • Workers return conflicting findings. Who resolves the conflict, and how?
  • One worker hangs or fails. Does the whole run fail? (timeouts, partial results, retry only that worker, report the gap)
  • Parallel agents modifying code or state: how do you avoid conflicts? (parallel reads, a single writer, isolated worktrees or branches)
  • Why not just give one agent a larger context window instead?
Still debated
  • Research-style tasks show clear gains from parallel sub-agents, while some builders argue tightly coupled work like coding goes better with a single agent, since parallel writers make inconsistent decisions.

SEARCH_ORDERS = {
    "name": "search_orders",
    "description": (
        "Find a verified customer's orders. Use before answering refund or shipping "
        "questions. Returns at most 10 orders, newest first. For a known order ID, "
        "use get_order instead."
    ),
    "input_schema": {
        "type": "object",
        "properties": {
            "customer_id": {"type": "string", "description": "From verify_identity, like 'cus_123'"},
            "status": {"type": "string", "enum": ["open", "shipped", "delivered", "refunded"]},
            "since": {"type": "string", "description": "ISO date, like 2026-08-01"},
        },
        "required": ["customer_id"],
    },
}

def search_orders(db, customer_id, status=None, since=None):
    if not customer_id.startswith("cus_"):
        raise ToolError("customer_id must look like 'cus_123'. Call verify_identity first.")
    orders = db.find_orders(customer_id, status=status, since=since, limit=10)
    if not orders:
        return "No orders match. Try removing the status or since filter."
    # Semantic fields only: no internal UUIDs, raw blobs, or unused columns
    return [{"order_id": o["id"], "status": o["status"], "total": o["total"], "placed": o["date"]}
            for o in orders]
Where depth is required
  • Two tools overlap. How does the model choose, and how would you fix it? (if an engineer can't say which applies, merge or sharpen the descriptions)
  • A tool can return 50,000 rows. What does the model see? (filters, pagination, summaries, or processing in code outside the context)
  • How do you make write tools safe to retry? (idempotency keys derived from the tool call ID)
  • How do you know a description change helped? (tool selection evals with both should-call and should-not-call cases)

Tool integration and protocols

How are tools discovered, loaded, and invoked, and how many can one agent handle?

OptionHow it worksBuys youCosts youReach for it when
Native function definitionsTools defined in application code and sent with requestsSimple, full controlIntegrations duplicated across appsA few app-specific tools
MCP serversStandard protocol for exposing tools, data, and prompts to any compatible hostReuse integrations across products; large ecosystemEvery loaded definition costs tokens; third-party servers are a trust decisionIntegrations shared across agents or teams
Deferred loading / tool searchDefinitions stay out of context; the model searches and loads what it needsLarge libraries without context bloatAn extra step; search can missDozens to hundreds of tools
Code execution over toolsTools exposed as a code API; the model writes a script that runs in a sandbox and returns only resultsLarge token savings; loops, filters, and joins without round tripsRequires a secure sandbox; individual calls are harder to approveData-heavy multi-step workflows
Skills (progressive disclosure)Short descriptions upfront, full instructions and scripts loaded on demandMany capabilities with small baseline contextDiscovery depends on descriptionsProcedures needed occasionally
Long-running tool tasksA call returns a handle; the client polls, updates, or cancelsWork that outlasts a requestState on both sidesBuilds, exports, batch jobs
Where depth is required
  • 200 tools across 12 MCP servers. What is in context on the first turn? (tool search or scoped server sets; measure definition tokens)
  • A third-party server returns text instructing the agent to act. What stops it? (tool output is untrusted data; see security)
  • How do a user's credentials reach a remote tool server? (per-user OAuth with scoped tokens, never placed in prompts)
  • When is code execution the wrong choice? (single simple calls, per-action human approval, no sandbox available)
Still debated
  • Direct tool calling vs code execution as the default interface. Code execution saves tokens and adds composability, but moves risk into a sandbox and makes individual actions less visible.

How does the agent find the knowledge it needs, and how do you know answers come from it?

Hybrid search + rerankingKeyword and vector results merged, then rerankedHandles exact terms (IDs, names) and paraphraseMore infrastructure and latencyEnterprise search with mixed query types
Agentic searchThe model issues several queries, reads, and refinesMulti-hop questions; recovers from poor first queriesSlower, costlier, can wanderResearch and investigation
Just-in-time referencesKeep paths, IDs, and URLs; load content with tools like grep or SQL when neededAlways fresh; no index to maintainNeeds good navigation toolsCodebases, databases, file systems
Structured sourcesText-to-SQL, APIs, semantic layers, knowledge graphsExact answers and aggregationSchema understanding and query safetyNumbers, joins, reporting

Where depth is required
  • How do you enforce document permissions? (filter by the user's access at query time, never after generation)
  • The index is a day stale and a policy changed. What happens? (freshness metadata, change capture into the index, live lookups for volatile data)
  • How do you chunk contracts vs code vs chat logs? (structure-aware chunking, retrieve the parent section)
  • How do you evaluate retrieval separately from generation? (recall on labeled queries, then answer grading)
Still debated
  • Precomputed vector indexes vs agentic just-in-time search. Indexes are faster; live exploration avoids staleness and index maintenance. Many systems use both.

Reference skeleton
def compact(llm, messages, window, threshold=0.8, keep_recent=6):
    if count_tokens(messages) < threshold * window:
        return messages

    cut = max(len(messages) - keep_recent, 0)
    while 0 < cut < len(messages) and messages[cut]["role"] == "tool":
        cut -= 1                        # never separate a tool result from its call
    older, recent = messages[:cut], messages[cut:]

    # Lightest step first: clear raw tool output the model has already used
    cleared = [{**m, "content": "[tool result cleared]"} if m["role"] == "tool" else m
               for m in older]
    if count_tokens(cleared + recent) < threshold * window:
        return cleared + recent

    summary = llm.generate([{"role": "user", "content": COMPACTION_PROMPT + render(older)}]).text
    return [{"role": "user", "content": "Summary of work so far:\n" + summary}] + recent

COMPACTION_PROMPT = (
    "Summarize this agent session for a successor with no other context. Keep: the goal, "
    "decisions and why, current plan, open problems, files or records touched, and exact "
    "identifiers. Drop: raw tool output already acted on, and dead ends (list them briefly).\n\n"
)
Where depth is required
  • Why not simply use the largest context window available? (recall and reasoning degrade as context grows; cost and latency rise)
  • What must survive compaction for a coding agent? (goal, decisions and reasons, current plan, open bugs, touched files, exact identifiers)
  • How does compaction interact with prompt caching? (rewriting history invalidates the cache from that point; compact rarely and keep the prefix stable)
  • How do you test a compaction prompt? (replay long traces and ask probe questions about earlier facts; maximize recall, then precision)

Still debated
  • Explicit, user-visible memory vs automatic background extraction. Automatic feels seamless but is harder to trust, audit, and correct.

Reference skeleton
RISKY = {"send_email", "issue_refund", "delete_record"}

def execute_gated(call, user, policy, approvals, tools):
    decision = policy.check(user, call.name, call.args)       # deterministic code, not the model
    if decision == "deny":
        return {"error": f"{call.name} is not permitted for this user."}

    if call.name in RISKY or decision == "needs_approval":
        digest = hashlib.sha256(
            json.dumps([call.name, call.args], sort_keys=True).encode()).hexdigest()
        approval = approvals.get(call.id)
        if approval is None:
            approvals.request(call.id, user=user, tool=call.name, args=call.args,
                              digest=digest, ttl_seconds=900)
            return {"pending": "approval requested"}          # durable pause point
        if (not approval["granted"] or approval["digest"] != digest
                or approval["user"] != user or approval["expires"] < time.time()):
            return {"error": "Approval missing, expired, or for different arguments."}

    # The call ID doubles as the idempotency key, so a replay after a crash is safe
    return tools.execute(call.name, call.args, idempotency_key=call.id)
Where depth is required
  • The worker crashed after calling the refund API but before recording the result. What happens on resume? (idempotency key on the call; record intent before and result after)
  • How do you ensure the executed action is exactly what was approved? (bind approval to a hash of tool and arguments, the user, and an expiry)
  • A run lasts three days and you deploy new workflow code. What breaks? (versioned workflows, replay compatibility)
  • Reviewers approve everything after a week. How do you keep approvals meaningful? (gate by risk, show clear diffs, sample audits)

Reference skeleton
def pass_at_k(n, c, k):
    """Chance at least one of k sampled trials succeeds, from n trials with c successes."""
    if n - c < k:
        return 1.0
    return 1 - comb(n - c, k) / comb(n, k)

def pass_hat_k(n, c, k):
    """Chance all k sampled trials succeed. The reliability metric for user-facing agents."""
    return comb(c, k) / comb(n, k)

def summarize_suite(results, k=3):
    # results: {task_id: [True, False, ...]} with at least k trials per task
    rows = {t: (len(r), sum(r)) for t, r in results.items()}
    suspect = [t for t, (n, c) in rows.items() if c == 0]   # 0% often means a broken task
    return {
        "pass@1": sum(c / n for n, c in rows.values()) / len(rows),
        f"pass@{k}": sum(pass_at_k(n, c, k) for n, c in rows.values()) / len(rows),
        f"pass^{k}": sum(pass_hat_k(n, c, k) for n, c in rows.values()) / len(rows),
        "check_these_tasks": suspect,
    }
Where depth is required
  • The agent succeeds 75% per trial. What is the chance it succeeds on all of three tries, and why does that matter? (0.75³ ≈ 42%; consistency is what users experience)
  • How many tasks do you need to begin? (a few dozen drawn from real failures; early changes have large effects)
  • A task fails every one of many trials. What do you suspect first? (a broken task or grader)
  • How do you keep trials independent? (a clean environment per trial; no leftover files, caches, or history)
  • How do you decide whether to adopt a new model? (run both suites; compare quality, cost per task, and latency)
Still debated
  • How much to rely on LLM judges. They scale well but share model blind spots, so teams differ on how often to recalibrate against humans.

Staff-level themes

These apply to every prompt. Raising them with specifics is much of what separates a staff answer.

When not to build an agent
A single call or a fixed workflow is often cheaper, faster, and more reliable. Autonomy should be justified by the task shape and confirmed by evals.
Nondeterminism as a design input
Plan for variance: idempotent tools, verification steps, retries with limits, and reliability measured as pass^k rather than one lucky run.
Trust boundaries and provenance
Every token has an origin: developer, user, retrieved content, tool output, memory, or another agent. Permissions should follow provenance.
Blast radius of actions
Separate reversible from irreversible actions. Use per-user credentials and make approval proportional to consequence.
Cost per completed task
Include retries, failures, escalations, and human review. Cheap calls in an expensive loop are not cheap.
Model churn
The harness should outlive any model. Evals turn a model upgrade into a quick decision, and scaffolding that compensates for weaker models should be easy to remove.
Degradation modes
Provider outages and rate limits happen. Decide in advance between a fallback model, queuing, a deterministic path, or a clear failure.
Human experience
Approval fatigue, explaining what the agent did, and handing work back to people are design problems, not afterthoughts.
Identity and audit
Every action should be attributable to both a user and a specific agent, with enough trace data to reconstruct why it happened.

Dated reference points

Current as of September 2026. Verify before relying on these, since this area changes every few months.

MCP current specification
The 2026-07-28 revision made the protocol core stateless, added an extensions framework (including Tasks for long-running work and MCP Apps for server-rendered UI), and hardened OAuth-aligned authorization.
Protocol governance
MCP and A2A are both hosted under the Linux Foundation. A2A reached a stable v1.0 specification and reported more than 150 supporting organizations by April 2026.
Tool definition overhead
Anthropic reported a five-server example with 58 tools consuming about 55K tokens before any conversation. Deferred tool search cut definition tokens by roughly 85%; a code-execution example dropped from about 150K to 2K tokens.
Multi-agent token cost
Anthropic's multi-agent research system was reported to use roughly 15 times the tokens of a chat interaction.
Sub-agent return size
Workers that explore with tens of thousands of tokens typically return condensed summaries of about 1,000 to 2,000 tokens.
Starting an eval suite
Anthropic recommends starting with about 20 to 50 tasks drawn from real failures, since early changes have large effects.
Prompt injection status
Meta published the Agents Rule of Two in October 2025. Researchers from several labs showed the same month that adaptive attacks bypassed a dozen published defenses.
Durable execution options
Temporal, Inngest, Restate, and DBOS are common choices, alongside durable workflow offerings from major cloud providers and checkpointing in agent frameworks.
